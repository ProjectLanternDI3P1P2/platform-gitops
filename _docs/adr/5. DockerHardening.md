# Docker Image Hardening and Kubernetes Deployment, Lantern Project

Practical guide for developers and infra. CI: GitHub Actions.

Version 3.0, September 24, 2026

## How to read this guide

- 🔴 **Required**: blocks the release if not respected.
- 🟡 **Recommended**: strongly advised, an exception is possible if justified with security.

Sections 1 to 9 match tasks T03.1 to T03.9 (image hardening). Sections 10 to 14 cover the Kubernetes deployment that goes with it: even a well-hardened image stays vulnerable if it's badly deployed.

---

## 1 · Base image selection (T03.1)

🔴 Use an official, maintained base image, and pin it by **tag + digest** (not just a tag, since a tag's content can change).

```dockerfile
FROM node:22-bookworm-slim@sha256:REPLACE_WITH_REAL_DIGEST
```

🟡 Prefer a smaller variant (`slim`, `alpine`, `distroless`) if it still covers the service's real needs (libraries, debug tools). Don't pick a variant based on size alone: Alpine (musl) can break native modules built for glibc.

**How to get the digest:**
```bash
docker pull node:22-bookworm-slim
docker inspect node:22-bookworm-slim --format='{{index .RepoDigests 0}}'
```

**Keep up to date:** review date, owner responsible for updating the base image.

## 2 · Remove unnecessary components (T03.2)

🔴 Multi-stage build: one stage compiles/installs, another one only pulls in what is strictly needed to run. Don't keep compilers, Git, or test tools in the final image.

🔴 `.dockerignore` is required, so you don't send useless (or sensitive) files to the builder:

```text
.git
**/node_modules
**/.env*
**/*.key
secrets/
coverage/
**/*.log
```

🔴 Locked dependencies and a reproducible install (versioned lockfile, `npm ci` instead of `npm install`).

Multi-stage example:

```dockerfile
# syntax=docker/dockerfile:1
FROM node:22-bookworm-slim@sha256:REPLACE AS dependencies
WORKDIR /build
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

FROM node:22-bookworm-slim@sha256:REPLACE AS runtime
WORKDIR /app
COPY --from=dependencies /build/node_modules ./node_modules
COPY package.json server.js ./
COPY src/ ./src/
```

**Check:** `docker history <image>` should not show a layer with build tools in the final image.

## 3 · Run as non-root user (T03.3)

🔴 The app runs as a dedicated, non-root user, with a fixed UID/GID. The code cannot be modified by that account.

```dockerfile
RUN groupadd --gid 10001 app \
    && useradd --uid 10001 --gid 10001 --no-create-home --shell /usr/sbin/nologin app

COPY --chown=0:0 . .
RUN chmod -R go-w /app

USER 10001:10001
EXPOSE 8080
CMD ["node", "server.js"]
```

🟡 Use a port > 1024 (e.g. 8080) so the app doesn't need extra privileges to listen on it.

**Check:**
```bash
docker run --rm <image> id
# should return uid=10001 gid=10001, never 0 (root)
```

## 4 · Vulnerability scanning (T03.4)

🔴 Scan the image **after the build**, on the published digest, with [Trivy](https://trivy.dev/). Any **HIGH** or **CRITICAL** vulnerability blocks the release, unless there's a documented exception.

```bash
trivy image --severity HIGH,CRITICAL --exit-code 1 <image>@<digest>
```

🟡 Also lint the Dockerfile with [Hadolint](https://github.com/hadolint/hadolint). It catches build mistakes, but it's not a security check on its own.

**Position on CVEs with no fix available:** by default, don't ignore them (`--ignore-unfixed` is not used). If a fix truly doesn't exist yet, open a documented exception with a review date, instead of silently ignoring it.

See section 10 (GitHub Actions) for how this fits into CI.

## 5 · Secrets management (T03.5)

🔴 No secrets in `ARG`, `ENV`, a copied file, or a command shown in the logs. Deleting a file in a later layer does not remove it from earlier layers of the image.

🔴 If the build needs private access (private npm registry, private Git repo), use a **BuildKit** secret, never an `ARG`:

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc,required=true \
    npm ci --omit=dev
```

```bash
docker build --secret id=npmrc,src=/protected/path/.npmrc -t api:build .
```

🟡 Also scan for forgotten secrets in the repo/image:

```bash
trivy fs --scanners secret --exit-code 1 .
trivy image --scanners secret --exit-code 1 <image>@<digest>
```

**Check:** `docker history --no-trunc <image>` should show no secret value in any layer's command.

## 6 · Image signing and provenance (T03.6)

🔴 Sign the image **after** it has passed validation (scans + tests OK), not before. The signature proves who published the image, not that it's free of flaws.

🔴 Generate an SBOM (component inventory) and provenance (how the image was built) at build time:

```bash
docker buildx build \
  --sbom=true \
  --provenance=mode=min \
  --tag "$IMAGE_REPOSITORY:$GIT_SHA" \
  --metadata-file build-metadata.json \
  --push .

IMAGE_DIGEST=$(jq -r '."containerimage.digest"' build-metadata.json)
```

🔴 Sign with [cosign](https://docs.sigstore.dev/cosign/), in **keyless** mode using the GitHub Actions identity (no private key to manage):

```bash
cosign sign "$IMAGE_REPOSITORY@$IMAGE_DIGEST" --yes
cosign verify "$IMAGE_REPOSITORY@$IMAGE_DIGEST" \
  --certificate-identity-regexp "https://github.com/<org>/<repo>/.*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"
```

All of this is already wired into the GitHub Actions workflow in section 10.

## 7 · Configuration hardening (T03.7)

This point covers two levels, both need to be done:

**In the image (Dockerfile):**
- 🔴 Use exec form for `CMD`/`ENTRYPOINT` (`["node", "server.js"]`, not `node server.js`), so the app correctly receives `SIGTERM` on shutdown.
- 🔴 Non-sensitive config through `ENV`, never a secret in plain text.
- 🟡 Optional `HEALTHCHECK` in the Dockerfile. It does not replace Kubernetes probes (section 11).

**In the deployment (Kubernetes Pod):** see section 11, the Pod's `securityContext`. This is a different, complementary layer, handled in the deployment YAML, not in the image.

## 8 · Documentation and CI integration (T03.8)

🔴 Each service keeps a service sheet up to date, so infra can deploy without guessing:

| Info | Example |
| --- | --- |
| Service / owner | `api`, Lantern Backend team |
| Runtime | Node.js 22, base `node:22-bookworm-slim` |
| Internal port | 8080 |
| Startup | `node server.js`, UID/GID 10001 |
| Expected secrets | `DB_PASSWORD` (mounted file) |
| Temporary writes | `/tmp` |
| Health endpoints | `/health/live`, `/health/ready` |

🔴 CI (GitHub Actions) automatically runs: lint → tests → build → scan → sign. See the full workflow in section 10.

## 9 · Registry policy (T03.9)

🔴 Push access is reserved to CI accounts/bots, not to developers pushing locally. Kubernetes nodes only get **read** access.

🔴 Always deploy by **digest**, never by tag (`:latest` or any other mutable tag):

```yaml
image: registry.example.com/lantern/api@sha256:REPLACE_WITH_DIGEST
```

🟡 Protect tags against overwrite if the registry supports it, and keep old versions around for rollback (with their signature and scan report).

## 10 · CI GitHub Actions: the full workflow

This workflow builds, scans, signs and publishes the image on every push to `main`. A separate job can then use the resulting digest to deploy.

```yaml
# .github/workflows/build-and-secure.yml
name: Build, scan and sign image

on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write   # push to the registry
  id-token: write   # keyless cosign signing (GitHub OIDC)

env:
  IMAGE_REPOSITORY: ghcr.io/${{ github.repository }}

jobs:
  build-scan-sign:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Lint Dockerfile
        uses: hadolint/hadolint-action@v3.1.0
        with:
          dockerfile: Dockerfile

      - name: Scan repo for secrets
        uses: aquasecurity/trivy-action@0.24.0
        with:
          scan-type: fs
          scanners: secret
          exit-code: 1
          scan-ref: .

      - name: Registry login
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Setup Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build and push (with SBOM + provenance)
        id: build
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ env.IMAGE_REPOSITORY }}:${{ github.sha }}
          sbom: true
          provenance: mode=min

      - name: Vulnerability scan (blocking)
        uses: aquasecurity/trivy-action@0.24.0
        with:
          image-ref: ${{ env.IMAGE_REPOSITORY }}@${{ steps.build.outputs.digest }}
          severity: HIGH,CRITICAL
          exit-code: 1

      - name: Secret scan on the image (blocking)
        uses: aquasecurity/trivy-action@0.24.0
        with:
          image-ref: ${{ env.IMAGE_REPOSITORY }}@${{ steps.build.outputs.digest }}
          scanners: secret
          exit-code: 1

      - name: Install cosign
        uses: sigstore/cosign-installer@v3

      - name: Sign the image (keyless, GitHub identity)
        run: |
          cosign sign --yes \
            "${IMAGE_REPOSITORY}@${{ steps.build.outputs.digest }}"

      - name: Verify the signature
        run: |
          cosign verify \
            --certificate-identity-regexp "https://github.com/${{ github.repository }}/.*" \
            --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
            "${IMAGE_REPOSITORY}@${{ steps.build.outputs.digest }}"

      - name: Published digest
        run: echo "Image ready: ${IMAGE_REPOSITORY}@${{ steps.build.outputs.digest }}"
```

**What this workflow does, in order:**
1. Lint the Dockerfile (Hadolint).
2. Look for forgotten secrets in the source code.
3. Build the image and push it, with SBOM and provenance generation.
4. Scan the published image by digest for vulnerabilities, blocks on HIGH/CRITICAL.
5. Scan the final image for secrets (in case one slipped into a layer).
6. Sign with cosign in *keyless* mode: no private key to store, GitHub provides the identity through OIDC.
7. Verify the signature right away, to be sure it's valid before considering the image releasable.

**Deployment job (example, adapt to your own method: direct kubectl, Helm, or GitOps):**

```yaml
  deploy:
    needs: build-scan-sign
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to the cluster
        run: |
          kubectl set image deployment/api \
            api=${IMAGE_REPOSITORY}@${{ needs.build-scan-sign.outputs.digest }} \
            -n lantern-app
          kubectl rollout status deployment/api -n lantern-app --timeout=300s
```

## 11 · Kubernetes deployment: minimum secure configuration

A hardened image that's badly deployed stays vulnerable: Kubernetes doesn't fix the Dockerfile for you, and a Pod with too many privileges cancels out the work done on the image.

🔴 These settings are required in the Pod's and container's `securityContext`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: lantern-app
spec:
  replicas: 2
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      serviceAccountName: api
      automountServiceAccountToken: false   # unless the app calls the Kubernetes API
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: api
          image: registry.example.com/lantern/api@sha256:REPLACE_WITH_DIGEST
          ports:
            - containerPort: 8080
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits: { cpu: "1", memory: "512Mi" }
          readinessProbe:
            httpGet: { path: /health/ready, port: 8080 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health/live, port: 8080 }
            periodSeconds: 10
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir: { sizeLimit: 64Mi }
```

**Key points to remember:**
- `readOnlyRootFilesystem: true` means any folder the app needs to write to (cache, tmp) needs its own volume, otherwise it will crash on startup.
- `capabilities.drop: [ALL]` removes all default Linux privileges; the app almost never needs any of them.
- Always set a `readinessProbe` and a `livenessProbe`, pointing at lightweight endpoints that don't expose anything sensitive.

## 12 · Secrets and networking (Kubernetes)

🔴 Application secrets (DB passwords, API keys) go through a Kubernetes `Secret` object, mounted as a file rather than an environment variable whenever possible:

```bash
kubectl -n lantern-app create secret generic api-database \
  --from-file=password=/protected/path/password
```

🔴 Deny network traffic by default, then explicitly open the flows you actually need (NetworkPolicy), if the cluster's CNI enforces them:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: lantern-app
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

Then add a rule that only allows what the API actually needs (ingress traffic from the load balancer, egress to DNS and the database), following the same logic as above, adapted to your cluster's real labels.

🟡 Enable **Pod Security Admission** in `restricted` mode on the namespace, to stop another deployment from bypassing these rules:

```bash
kubectl label namespace lantern-app \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.31 --overwrite
```

## 13 · Checklist before release

- [ ] Official, maintained base image, pinned by digest.
- [ ] Multi-stage build, `.dockerignore` in place, locked dependencies.
- [ ] Fixed non-root user, code cannot be modified by that account.
- [ ] No secret in the Dockerfile, the logs, or any image layer.
- [ ] Trivy scan passed (HIGH/CRITICAL) on the published digest.
- [ ] SBOM + provenance generated, image signed with cosign, signature verified.
- [ ] Service sheet up to date.
- [ ] Kubernetes deployment by digest, hardened `securityContext` applied.
- [ ] Readiness/liveness probes in place.
- [ ] Default-deny NetworkPolicy with the needed flows opened.

## 14 · Quick troubleshooting

| Symptom | Check first |
| --- | --- |
| `ImagePullBackOff` | Correct name/digest, node access to the registry |
| `CrashLoopBackOff` | Pod logs, startup command, permissions |
| `Permission denied` | UID/GID, permissions on the mounted volume |
| `Read-only file system` | App is writing outside the volumes it was given |
| `OOMKilled` | Memory limit set too low for the real need |
| CI scan is blocking | Real HIGH/CRITICAL CVE: fix the base image/dependency, or open a documented exception |
| Signature rejected at deploy time | Check the image was actually signed by the right GitHub workflow |
