# ADR 6: Image admission chain (scanned, signed and traceable images only)

Date: 2026-11-25
Status: Accepted, partially implemented (see "Implementation status")
Related: [Image admission policy](../../security/Image%20admission%20policy.md), [runbook](../technical/image-admission-runbook.md), US-05

## Context

Container images built by the CD pipelines are published to Harbor (`10.4.111.200:18443`, project `lantern`) and deployed on the K3s cluster by Argo CD. Until now nothing proved that a deployed image had been scanned, came from our pipeline or had not been replaced after publication. A tag such as `main-latest` can point to a different image at any time.

The environment imposes constraints that drive the choices below: the runners and the cluster reach the internal Harbor, but have no access to public transparency services; Harbor uses a self-signed certificate; there is one shared CD workflow (`publish-and-promote`) used by all services.

## Decisions

### 1. Block CRITICAL vulnerabilities, review the threshold later
Harbor scans every push (Trivy). Images with CRITICAL vulnerabilities are blocked, both by Harbor (pull refused, HTTP 412) and by the CD (no signature if CRITICAL).
- Alternative considered: block HIGH from the start. Rejected for now: the images deployed today still contain HIGH vulnerabilities (for example v2.3.1 of Dungeon: 53 findings, 29 fixable), blocking them would stop running workloads. The threshold is reviewed periodically and may be lowered to HIGH.

### 2. Scan gate in the CD, before the signature
The shared workflow waits for the Harbor scan result through the Harbor API and stops on CRITICAL, on scan error or on timeout. Signing only happens after this step ("scan before sign").
- Alternative considered: scanning only in CI (US-04). Kept as a separate control: CI scans the source and the build, the Harbor scan covers the image that is really published and is the one that is enforced at pull time.

### 3. Signature with cosign, key-based, by digest
Every image is signed by the CD with cosign, by digest, then verified right after with the CI public key.
- Alternative considered: keyless signature (OIDC, Fulcio and Rekor). Rejected: it needs access to public Sigstore services, which the restricted network does not allow, and a public transparency log would expose internal image names.
- Alternative considered: Notation. Not retained: cosign is supported by Harbor and by the usual Kubernetes policy engines, and the team had no need for a second tool.
- Signing by digest, never by tag: a tag can move, a digest cannot.

### 4. Trusted identity is the CI signing key
Only signatures made with the CI key are trusted. Harbor's own verification only checks that a signature exists, not who made it, so the identity check is done by the policy engine on the cluster (US-07, task T05.4).

### 5. Key storage and rotation
The private key and its password live in the team vault (Vaultwarden, collection Security), which is the source of truth. A copy is stored as GitHub Actions secrets because the workflow runs on GitHub. The key is rotated every 12 months (next rotation: 2027-11-25) and immediately in case of compromise.
- Accepted risk: the copy in GitHub secrets can be read by anyone who can edit workflows of a repository that has access to the secret. This is why the secrets should be organization secrets with a limited scope and why workflow changes require review.

### 6. Immutable reference: digest in the GitOps repository
The CD sends the image digest to the promotion workflow, which writes it next to `newTag` in `apps/*/overlays/k3s/kustomization.yaml`. Kustomize gives priority to the digest, so what is deployed is exactly what was scanned and signed. A rollback is a revert to a previous digest. A stale digest is removed when a promotion arrives without digest, so it can never stay next to a new tag.
- The digest is optional while services migrate to the new workflow. It becomes mandatory once all services have migrated.

### 7. Provenance attestation
The CD attaches a signed SLSA v0.2 provenance attestation to the image digest (source repository, commit, workflow run, actor) and verifies it right after signing (same key, commit must match).
- Accepted limitation: the attestation is generated by the shared workflow itself. It proves the link between image, commit and run, but it does not come from an isolated builder, so it is not a SLSA level 3 guarantee.
- Alternative considered: the official SLSA generator. Not retained for now: it relies on public Sigstore services.

### 8. Emergency exceptions are time limited
A non compliant image can be deployed only through a documented exception: work item with the reason and risk, approval by the Security team, 7 days maximum, logged. In Harbor, the CVE allowlist of the project supports an expiry date.

### 9. Promotion through a pull request (proposed)
The promotion workflow cannot push on `main` any more: the repository ruleset "main: merge only" requires a pull request and two approvals. The proposal retained with the owners is a dedicated GitHub App that opens one pull request per promotion and enables auto-merge, so that the merge only happens after the GitOps validation passed. The App may bypass the review requirement for pull requests only, never push directly. Status: awaiting the creation of the App.

## Consequences

Benefits: a deployed image is traceable from the running pod to its commit; a vulnerable, unsigned or replaced image is detected before or at deployment; a rollback is exact.

Costs and risks accepted:
- No transparency log (`--tlog-upload=false`): there is no public, tamper-evident record of signatures. The control relies on the key and on Harbor's access control.
- `--allow-insecure-registry` is used because Harbor has a self-signed certificate. The real fix is to make the runners and the cluster trust the Harbor CA.
- The Trivy database changes over time: the number of fixable findings of an image can change without any new build. Images must be rescanned periodically.
- The CD uses one shared Harbor robot account for all services. A compromise of this account allows pushing to every repository of the project. Its rotation follows the 90 days rule of the Password policies (the robot currently has a one year expiry, to be aligned).
- Harbor blocking applies to every pull, including the pull robot of the cluster: an image that becomes blocked cannot be rescheduled (ImagePullBackOff). Hence the rule to check all deployed images before enabling a control.
- The image `keycloak-theme` is published by a separate workflow that does not sign: it must be migrated before enabling Cosign enforcement.
- Cosign verification fetches the signature and attestation artifacts of Harbor. Harbor tries to scan these small artifacts and reports a scan error on them. The impact of this with blocking enabled must be tested before the enforcement (T05.6).
